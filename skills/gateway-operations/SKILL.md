# Feishu Gateway Operations

Use the plugin MCP tools as the authoritative runtime source:

- Call `lark_gateway_status` for connection state, counters, queue depth, process details, and dashboard URL.
- Inbound work is serialized per Codex session ID. Two events assigned to the same Codex session wait for each other, while events assigned to different sessions run concurrently. Health reports `activeSessionCount`, `activeSessions`, and `currentEventIds`; `sessionQueueCount` counts session queues that currently contain active or waiting work. `queueDepth` remains the total number of inbound and outbound items waiting to start.
- Call `lark_gateway_events` for inbound, outbound, ignored, failed, or lifecycle records. Apply direction, kind, status, and query filters instead of reading raw log files.
- Use the existing Feishu `eventId` as the problem ID. Every stage for the same business event uses that value, including delayed topic-chat approval and its send result. Ask the user for this problem ID when diagnosing a reported gateway issue, and pass it to the events query. The dashboard highlights it in event details and provides a copy button. Each traffic record also retains its separate internal `id`.
- Chat traffic records include `chatId`, `larkThreadId`, `routeType`, `threadId`, and `threadTitle`. A `fixed_chat_route` sends an accepted ordinary-chat Bot event to the existing Codex task configured in `chatRoutes`. A `topic_thread_assignment` route means one Feishu `chatId + larkThreadId` pair owns one persistent Codex task. A new topic task receives one short chat-level initialization prompt, an explicit project Skill invocation when `skillName` is configured, and a one-time snapshot of messages and attachments available up to its triggering message. Later messages resume the task without repeating that material. A `chat_assignment` route is the automatic ordinary-chat behavior.
- Reused Codex tasks receive only the current Feishu message by default because their task history already contains earlier forwarded requests. The gateway reads and appends recent Feishu group or topic history only when the current message explicitly asks to view or use that history, such as “结合上面的日志” or `#带上下文`. A Feishu reply includes only the one message it directly replies to even without that request. `groupContextMessages` and `maxContextChars` limit explicitly requested history.
- Health output includes `fixedChatRouteCount` and `fixedChatRoutes`. Fixed ordinary chats remain Bot-event-only: group messages must explicitly mention the current Bot, and these chats never enter user-identity polling. A fixed route takes priority over a saved automatic chat assignment; startup removes that obsolete assignment without deleting the old Codex task.
- Health output includes `topicChatRouteCount`, `topicChatRoutes`, `topicThreadCount`, and `topicThreads`. A route's `verified` field becomes true after the gateway confirms its Feishu chat mode; `verifiedChatMode` reports that mode. Routes accept topic chats by default, while `allowRegularChat: true` explicitly allows a regular chat and creates one Codex task per root message or message thread. Health output reports `replyApprovalRequired`, `skillName`, and whether an initialization prompt is configured, but does not expose the prompt text. New assignments report `setupStatus`, `setupId`, the Skill content hash, initial message/image/file counts, and whether the initial snapshot was truncated. Assignments loaded from an older state report `legacy`; the gateway does not reinitialize or backfill them.
- When `userMessagePollingEnabled` is true, `pollChatIds` contains only chats configured in `topicChatRoutes`. The gateway reads every new user or external-application root message and topic reply in those chats with the authorized user identity, so those messages do not need to mention the Bot. It excludes the gateway Bot's own messages to prevent reply loops. Polling uses the raw chat-container message list because its time range includes topic replies; message IDs are then batch-read for formatted content before the cursor advances. `pollChatCount`, `pollingState`, `lastPollAt`, and `lastPollError` show whether those reads are current.
- Chats listed only in `allowedChatIds` are never polled. A group message from an ordinary chat enters the gateway only through a Bot event that explicitly mentions the current Bot. When that group is not configured yet, the gateway first writes its `chat_id` into `allowedChatIds` in the active private configuration, records a `chat_allowed` event, and then processes the same message. Point-to-point Bot events keep their existing behavior.
- `commandSenderCount` reports how many user `open_id` values are configured to issue explicit `@Bot` instructions. A matching message is marked as requiring a Codex reply even when another group member is already handling the topic; the IDs themselves are not exposed by health output.
- Every polled topic message reaches its assigned Codex task, and the Agent decides whether Bot intervention is useful. When the Agent returns exactly `[NO_REPLY]`, the gateway records a successful internal event with `stage=no_reply`, summary **Codex Agent 判断无需回复**, and the same Feishu `eventId`. Treat this as an intentional completed outcome, not as filtering, processing failure, or outbound delivery failure. The dashboard labels the stage **Agent 决定不回复**.
- Replies generated for a topic route are stored when its `replyApprovalRequired` setting is not `false`. Health reports `pendingOutboundCount`; the dashboard shows each pending reply. **授权发送** sends it with the Bot identity, while **拒绝授权** removes it without sending and records a `rejected` outbound event. A route with `replyApprovalRequired: false` sends each new reply immediately with the Bot identity; changing the setting does not send or remove replies already pending.
- Call `lark_gateway_dashboard` when the user wants the browser URL.
- Proactive Bot messages sent with `lark_gateway_send_message` appear as `queued`, `sending`, and `sent` or `failed` outbound records. Filter by `direction=outbound` and search by chat ID, message ID, or idempotency key when diagnosing them.
- Bot message recalls requested with `lark_gateway_recall_message` appear as `queued`, `recalling`, and `recalled` or `failed` outbound records. Search by the recalled message ID when diagnosing them.
- Chat messages use `messageId` as the shared business deduplication key across Bot events, user polling, and manual retry; each separate `eventId` remains available for tracing. A loopback-only `POST /api/messages/retry` diagnostic endpoint can re-read one exact Feishu `messageId` with the user identity, clear its saved business deduplication record once, create a fresh outbound idempotency scope, and enqueue it through the normal inbound pipeline. Use it only for an explicitly requested retry; it returns a conflict while that message is already queued or processing.
- A `thread/resume` JSON-RPC `-32600` response containing `already has an active writer` is retried with bounded exponential backoff inside the same Codex session queue. Intermediate conflicts are observable retry records, not failures; only the final exhausted attempt may produce one failure notice.
- IM replies and proactive Bot messages that fail with an explicit HTTP 429/rate-limit response are retried with bounded exponential backoff while reusing the same idempotency key. Intermediate attempts are `delivery_retry` processing records; Codex is not run again, and only exhaustion becomes a final outbound failure.
- Image-bearing inbound messages include internal `attachment_download_queued` and `attachment_downloaded` records. The image bytes are stored only under the gateway state directory and are passed to Codex as local image inputs; the traffic record reports counts and sizes, not a public URL.
- Before starting each Codex App Server process, the gateway reads the active provider and its `env_key` from the user's `~/.codex/config.toml`. When that variable is absent from the gateway process, it resolves the value from the operating-system user environment on Windows or macOS and passes it only to the Codex child process. Missing variables fail before a Codex turn starts and the error names the variable without exposing its value.

The plugin MCP process starts the gateway and dashboard when they are not already healthy. Do not start a second gateway process manually after a tool reports a healthy service.

When explaining a missing response, distinguish these stages explicitly: event received, filtered, queued, Codex processing, sending, sent, and failed. Cite the event time and business ID when present.

Traffic content is stored locally under `%LOCALAPPDATA%\lark-codex-gateway\traffic.ndjson`. Do not expose that file outside the machine or copy its message content into unrelated systems.
